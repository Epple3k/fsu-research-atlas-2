01 / The problem

Research lives in papers. Its patterns live between them.

38,607 publications are easy to count and difficult to understand together. A strategist often needs to discover the connections between fields before knowing which papers to search for.

Existing publication databases are useful when the user already knows what paper, author or subject to search for. They are less useful for exploratory questions: Which fields are becoming more interdisciplinary? Where are strong connections forming? What evidence supports that conclusion?

A conventional node-link graph adds a second difficulty: with 26 fields and 279 relationships, a weave of arcs can still be hard to compare. Putting conversational AI on top introduces a third difficulty: a fluent answer may hide its evidentiary trail.

How might someone notice an unexpected intersection, understand how substantial it is, and inspect the actual work, all within a single line of inquiry?

Provisional primary user

A university research strategist investigating cross-disciplinary activity before deciding where to focus outreach or further analysis. This user definition is a design hypothesis until interviews with research-adjacent users are completed.

JOB 01

Identify a relationship worth investigating without scanning thousands of papers.

JOB 02

Understand whether a claim describes current volume, change over time or interpretation.

JOB 03

Inspect the exact papers behind a conclusion before acting on it.

02 / Hypothesis

Make the relationship the unit of discovery.

The useful unit here is not a single paper or a floating node. It is a crossing: two research fields sharing a documented set of works.

The visual system should let a user perceive the landscape before asking a question, then move from field to crossing to actual publications without losing context. A matrix uses negative space to show missing links as clearly as strong ones; optional AI helps phrase questions but does not supply unverified counts.

03 / Working product

From crossing map to source record.

This is the real data-backed instrument. Darker intersections contain more shared publications. Switch to a time-window comparison, search a discipline or paper title, and select a crossing to inspect its source records.

If the embedded view feels tight, open the prototype full-screen. The interface falls back to a deterministic interpreter if the hosted AI service is waking or unavailable.

04 / Design decisions

Why a crossing field instead of a network tangle?

The old radial graph looked interconnected but made differences hard to judge. A field-by-field matrix turns “how much do these two areas overlap?” into a direct visual lookup.

Claims are objects, not prose.

An AI answer is decomposed into selectable claims. Selecting one highlights the exact field relationship and loads its supporting papers.

Tradeoff: the response is less conversational, but far easier to inspect and challenge.

One square, one inspectable crossing.

A matrix gives every field pair an address. Intensity shows shared publication volume; empty cells show where no relationship was recorded. Selecting a cell opens the evidence inspector.

Tradeoff: the matrix is less theatrical than a radial graph, but easier to compare. Both axes repeat the same fields for lookup.

Start with data, not a waiting screen.

The map, field search, title search and source lookup use the local OpenAlex records. Optional AI never prevents exploration when the backend is asleep.

Tradeoff: a local interpreter supports fewer question phrasings than a general model, but the core task remains responsive and verifiable.

The model never owns the numbers.

The agent can only call constrained tools that return observations, field pairs and work IDs. The browser reconstructs visible claims from its own data before rendering them.

Tradeoff: this limits free-form expression, but makes unsupported quantitative claims structurally harder to display.

05 / Iteration

A failure in the evidence chain changed the implementation.

A technically correct answer is still a product failure if the interface cannot expose how it was produced.

Observed failure

The agent answered an open-ended question with real tool output, but the UI rendered no clickable evidence.

The first server implementation only collected provenance when the model used a direct link lookup. For “most interconnected” questions, the model used a top-collaborations tool instead. The prose contained supported values, but the returned edge list was empty—breaking the product’s core promise.

I changed the server to capture evidence-backed field pairs from every relevant tool result and kept claim construction in the browser. I also raised the model’s output budget after tracing a second failure where tool calls were silently truncated on harder questions. The iteration was not “make the AI sound better.” It was “make the evidence contract survive different agent behavior.”

06 / Evaluation

Next: test whether visible provenance changes behavior.

The working product proves the mechanism. It does not yet prove that the mechanism improves comprehension or calibrated trust.

The original study protocol proposes a claim-only control and an evidence-first view with source links. It was drafted before the crossing-map redesign, so the tasks and materials need revision before running sessions. The intended six to eight participant comparison remains a plan, not a reported result.

What would count as learning

If evidence visibility raises trust indiscriminately, the design may create false confidence rather than calibrated trust. More encouraging evidence would be that participants verify sources more often, explain conclusions more accurately and describe clearer reasons for trusting or questioning a claim.

The study protocol, moderator script and session record are included in the public repository so the evaluation can be reviewed and repeated.

No results are claimed yet. This case study will be updated after sessions are completed; placeholders are intentionally not presented as findings.
07 / Reflection

Trust is something an interface lets a user do.

The resolution is a crossing map where the visual pattern and its proof live in one continuous interaction.

This prototype taught me to treat data provenance as a user interaction rather than a backend property. A citation stored somewhere in the system is not enough. The person using the product needs a visible path from question, to claim, to relationship, to source—and that path must survive the unpredictable ways an agent may choose to solve a problem.

The next iteration should test real investigations: Can a newcomer discover a field pair, interpret its shading, notice missing relationships, distinguish unequal time windows, and open a source before trusting a summary?
